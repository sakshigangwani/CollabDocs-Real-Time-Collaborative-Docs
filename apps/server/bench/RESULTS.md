# Benchmark results (2026-09-27)

Environment: one Apple M4 laptop (10 cores, 16 GB), Node 24, PostgreSQL 18.1 + pgvector 0.8.1,
Redis 7 (local). Load generators, servers, Postgres and Redis all share the machine, so absolute
numbers are conservative and not comparable to a multi-host deployment.
All runs use the isolated `collabdocs_bench` database (see `guard.ts`).

## Real-time collaboration (`apps/web/bench/collab-load.mjs`)
> The table below was measured on the earlier Yjs/Hocuspocus stack. The benchmark now drives
> OT clients (prosemirror-collab over the server's WebSocket protocol); re-run it to refresh
> the numbers. A 100-editor smoke run on OT: cross-instance p50 2.1 ms, p99 10 ms, 10/10 converged.

Real `HocuspocusProvider` clients, 10 editors per doc, 1 edit/s per editor, 30 s measured after 5 s
warm-up. Editors of each doc alternate between instances, so most updates cross Redis.
Latency = receiver wall clock − sender timestamp (same host clock).

| Editors | Instances | Deliveries/s | p50 | p95 | p99 | Converged |
|---|---|---|---|---|---|---|
| 500  | 2 | 4.5K  | 2.0 ms | 8.3 ms | 15 ms  | 50/50 |
| 1,000 | 2 | 9.0K  | 1.3 ms | 8.4 ms | 58 ms  | 100/100 |
| 2,000 | 2 | 18.0K | 1.0 ms | 7.9 ms | 206 ms | 200/200 |
| 4,000 | 2 | 36.0K | 1.3 ms | 331 ms | 718 ms | 400/400 |
| 4,000 | 4, editors spread across instances | 34.5K | ~850 ms | ~2.4 s | ~2.8 s | 400/400 |
| 4,000 | 4, doc-affinity (all editors of a doc on one instance) | 36.0K | 0.9 ms | 60 ms | 321 ms | 400/400 |

Cross-instance hop via Redis adds ~1–2 ms at p50 (e.g. 2K: same-instance 0.58 ms vs cross 1.48 ms).
At 4K on 2 instances the single-threaded servers hit 100% CPU in bursts. With 4 instances
and editors spread across all of them, every instance still processes every update, so per-instance
CPU rose to ~88%. Doc-affinity routing dropped it to ~26%. Doc-affinity is a load-balancer policy
that the app does not implement yet.

## Search (`search-bench.ts`, `api-bench.mjs`)
10,000 docs (synthetic Zipf text, ~249 words each), 15,959 ACL rows, 200 users, 20 workspaces;
users can read 220–447 docs each.
- In-process handler, sequential, 1,000 queries × 5 classes: p50 75.7 ms, p95 135.9 ms.
- HTTP, concurrency 10, 1,000 queries: p50 118 ms, p95 171 ms.
- EXPLAIN ANALYZE: the planner drives from `DocumentAcl_principalId_idx` (260 docs), then evaluates
  `word_similarity()` on each doc body (~0.27 ms/doc), which accounts for ~99% of the 73 ms. Neither GIN
  trigram index is used, because `word_similarity(a,b) > x` is not indexable. Forcing the GIN path
  (`<%`) is worse (857 ms, 2,601 recheck rejects). FTS alone via GIN: 0.12 ms.

## RAG (`rag-eval.ts`, `rag-baselines.ts`)
The corpus (`rag-dataset.json`) was generated by gpt-4o-mini and has two fictional companies. Workspace A has
40 docs the eval user can read. Workspace B has 20 docs the user cannot read: 10 of them cover the same
topics as A. The index also holds 10K synthetic distractor docs, for 37,726 chunks in total.
Questions: 159 answerable (gold = chunk containing the verbatim evidence sentence), 19 answerable only from
restricted docs, and 20 unanswerable.
- Retrieval (production `retrieve()`, workspace scope): Hit@8 93.1%, MRR 0.672, doc Hit@8 95.6%.
- Retrieval latency incl. query embedding: p50 206 ms, p95 337 ms; SQL only: p50 3.9 ms, p95 4.6 ms.
- End-to-end `/ai/ask` (real handler, concurrency 4): p50 888 ms, p95 1.18 s.
- Answers judged correct (gpt-4o-mini judge vs gold): 145/159 (91.2%).
- Citations: 143/156 answered questions cite the gold chunk (91.7%); 0 out-of-range markers.
- Refusals: 20/20 unanswerable; 16/19 restricted-only questions refused; 0/19 cited an inaccessible doc.
- Baseline (exact kNN, no ACL): the restricted doc appears in the top 8 for 17/19 restricted questions, and the
  other company's docs appear in the top 8 for 91/159 normal questions. Production ACL-in-SQL retrieval: 0/19.
- Embedding pipeline: 10,060 docs → 37,726 chunks in 208 s (16 workers), 0 failures.
- Risk found: for a user who can read ~40% of the corpus, the planner switches to HNSW (ef_search=40) and then
  filters. Gold-doc hit rate drops to 11/159, against 152/159 for exact search (p50 52 ms). This is amplified by the synthetic
  cluster, so it is reported as a risk and not as a production number.

## API (`api-bench.mjs`, 2 instances, full middleware, concurrency 10, 1,000 requests each)
- GET /documents/:id: p50 2.7 ms, p95 4.9 ms.
- PATCH /documents/:id (title + tsvector reindex): p50 12.0 ms, p95 38.2 ms.
- Security checks: 5/5 expected statuses (401 / 200 via workspace ACL / 404 cross-tenant / 403 viewer
  edit / 403 missing CSRF).
- Distributed rate limit: 150 requests to instance A + the rest to B → first 429 at request 301 (limit 300/min).
